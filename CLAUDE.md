## Overview

This is the **MOSIP Android Registration Client** — a Flutter + Android tablet application that allows field officers to register citizens for national identity. It is the mobile counterpart to the MOSIP desktop Registration Client.

## Build & Run Commands

### Flutter (primary entry point)

```bash
# Install dependencies and generate code (run once after cloning)
bash pigeon.sh

# Run on connected device/emulator
flutter run

# Build APKs
flutter build apk --debug
flutter build apk --release

# Generate localization files (required after adding/modifying lib/l10n bundles)
flutter gen-l10n

# Regenerate Pigeon bridge files and build_runner outputs
dart run build_runner build --delete-conflicting-outputs
```

### Android Gradle (run from `android/` directory)

```bash
# Run all unit tests (own modules only: app, clientmanager, keymanager, packetmanager, transliterationmanager)
./gradlew testDebugUnitTest

# Run tests for a specific module
./gradlew :clientmanager:testDebugUnitTest

# Run a single test class
./gradlew :clientmanager:testDebugUnitTest --tests "io.mosip.registration.clientmanager.service.RegistrationServiceImplTest"

# Generate Jacoco coverage report for clientmanager
./gradlew :clientmanager:testDebugUnitTestCoverage

# Generate coverage for all own modules
./gradlew testDebugUnitTestCoverage

# SonarQube analysis
./gradlew sonar
```

### UI Automation Tests (ui-test/)

```bash
# Build the test JAR
cd ui-test && mvn clean package -DskipTests=true

# Run tests from packaged JAR (requires Appium server running)
cd ui-test/target && java -jar uitest-regclient-1.0.0.jar
```

## Architecture

### Two-Layer Design: Flutter UI + Android Native

The app uses **Flutter for the UI** and **Android (Java) for all business logic**, connected via [Pigeon](https://pub.dev/packages/pigeon) — a type-safe code generator for Flutter ↔ native method channels.

```
lib/                          # Flutter/Dart layer
├── main.dart                 # App entry, MultiProvider setup, InactivityTracker
├── app_router.dart           # Named route definitions
├── provider/                 # ChangeNotifier providers (state management)
├── platform_spi/             # Dart abstract interfaces for each native service
├── platform_android/         # Dart implementations calling Pigeon-generated code
├── ui/                       # All Flutter widgets and screens
├── model/                    # Pure Dart data models
├── pigeon/                   # Auto-generated Pigeon Dart files (do not edit)
└── utils/                    # App config, styles, constants

pigeon/                       # Pigeon input definitions (source of truth for bridge)
└── *.dart                    # One file per bridge domain (user, machine, biometrics…)

android/
├── app/                      # Flutter host app (MainActivity, Pigeon API registrations)
│   └── src/main/java/io/mosip/registration_client/
│       ├── MainActivity.java          # Registers all Pigeon APIs with FlutterEngine
│       ├── api_services/             # Pigeon interface implementations
│       └── model/                    # Auto-generated Pigeon Java files (do not edit)
├── clientmanager/            # Core business logic library
│   └── src/main/java/io/mosip/registration/clientmanager/
│       ├── config/           # Dagger DI modules (AppModule, RoomModule, NetworkModule)
│       ├── dao/              # Room database DAOs
│       ├── entity/           # Room entities
│       ├── repository/       # Repository layer wrapping DAOs
│       ├── service/          # Service implementations
│       ├── spi/              # Service interfaces
│       └── dto/              # Data transfer objects
├── keymanager/               # Cryptographic key management
├── packetmanager/            # Registration packet creation and encryption
└── transliterationmanager/   # Script transliteration
```

### Pigeon Bridge Pattern

Each domain has three files you must keep in sync:

1. `pigeon/<domain>.dart` — the source definition (edit here)
2. `lib/pigeon/<domain>_pigeon.dart` — auto-generated Dart (regenerated by `pigeon.sh`)
3. `android/.../model/<Domain>Pigeon.java` — auto-generated Java (regenerated by `pigeon.sh`)

After modifying any `pigeon/*.dart` file, re-run `bash pigeon.sh` to regenerate both sides.

The Dart implementation lives in `lib/platform_android/` (implements the SPI from `lib/platform_spi/`) and calls the generated Pigeon Dart class. The Java implementation lives in `android/app/src/main/java/.../api_services/` and implements the generated Pigeon Java interface. `MainActivity.java` registers each pair with the `FlutterEngine`.

### Dependency Injection (Android)

Dagger 2 is used across all Android modules. `AppModule` in `clientmanager` is the central DI module — it provides all singleton services. `AppComponent` (in `android/app`) assembles the full object graph and injects into `MainActivity`. When adding a new service, add a `@Provides @Singleton` method to `AppModule` and inject it via `@Inject` in `MainActivity`.

### State Management (Flutter)

Provider (`ChangeNotifier`) is used. The top-level providers are initialized eagerly in `main.dart`:
- `GlobalProvider` — locale/language, app-wide settings
- `AuthProvider` — login state, user roles, idle/grace time
- `SyncProvider` — master data sync state
- `RegistrationTaskProvider` — active registration session
- `ApprovePacketsProvider` — packet approval workflow
- `ConnectivityProvider` — network status

### Database

Room (SQLite via SQLCipher for encryption) in `clientmanager`. Entities, DAOs, and repositories follow the standard Room pattern. The database is initialized in `RoomModule`.

### Background Jobs

Sync jobs are scheduled using `AlarmManager` (exact alarms) from `MainActivity`. Job definitions and cron schedules come from `SyncJobDef` entities synced from the MOSIP server. `BatchJob` resolves the next execution time from the cron expression. `UploadBackgroundService` is the foreground service triggered by the alarm.

### BioSDK Loading

Biometric SDKs are distributed as AARs placed in `android/clientmanager/src/main/assets/biosdk/`. The Gradle task `dexifyBiosdkAars` converts these AARs to DEX JARs at build time so they can be loaded at runtime via `DexClassLoader` (Android requires DEX format, not raw bytecode).

## Key Configuration

- **Server URL**: Set in `android/build.gradle` → `ext.serverBaseURL`. For development, override in `android/local.properties`.
- **Signing**: Release signing requires `keyAlias`, `keyPassword`, `storeFile`, `storePassword` in `android/local.properties` (key.properties is also read).
- **App styling**: `lib/utils/app_style.dart` and `lib/utils/app_config.dart`.
- **Localization bundles**: `lib/l10n/` — run `flutter gen-l10n` after changes.

## Registration Processes

The app supports four process types (defined in `lib/ui/process_ui/process_type.dart`), each rendered by `GenericProcess`:
- New registration (`/new_process`)
- Update UIN (`/update_process`)
- Lost UIN (`/lost_process`)
- Correction (`/correction_process`)

The UI specification (field definitions, screens, validators) is driven by `ProcessSpec` data synced from the MOSIP server and stored in the local Room database.

## Testing Notes

- Own modules tested: `app`, `clientmanager`, `keymanager`, `packetmanager`, `transliterationmanager`. Third-party Flutter plugin subprojects have tests disabled.
- Tests use Robolectric 4.12.2, Mockito 5.11.0, and JUnit 4. JVM args for Java 21 compatibility are set in `build.gradle`.
- Jacoco coverage minimum threshold: 30% line coverage (enforced by `testDebugUnitTestCoverageVerification`).
- UI automation tests in `ui-test/` use Appium + TestNG and require a running Appium server and a configured device/emulator with Mock MDS installed.
